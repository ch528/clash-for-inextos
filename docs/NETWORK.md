# Network behavior

Mihomo Controller and Mixed Port bind to `127.0.0.1`. The browser reaches Zashboard through the authenticated Backend at `/dashboard/`; the controller secret is injected on the device and is never returned to the browser.

Settings reports the public global IPv6 on `ppp0`, or on the IPv6 default-route interface when `ppp0` is absent. It inspects the certificate served by the local `[::1]:8844` endpoint and reports SAN mismatch or expiry. It does not read, export, replace, or renew the TLS private key or certificate. The existing iNextOS Certbot path was verified on 2026-10-12: its daily timer is enabled, its deploy hook tests and reloads Nginx, and a staging renewal passed after the certificate was reissued for the current `ppp0` IPv6. The renewal configuration stores a literal IP; after that address changes it must be reissued for the new address. Router reboot behavior was not tested.

All capture settings are opt-in and default to off. TUN defaults to IPv4 and IPv6 routes, MTU 1500, and Auto Route enabled; Auto Redirect and Strict Route default off. Saving device or DNS preferences while capture is off does not change system DNS, default routes, policy rules, nftables, DHCP, or LAN forwarding. Capturing traffic starts the dedicated inextos-clash-mihomo.service; only that service receives CAP_NET_ADMIN and /dev/net/tun.

LAN proxy offers two modes: all LAN devices, with optional direct devices, or selected devices identified by MAC address. A direct IP entry becomes a leading SRC-IP-CIDR rule; a direct MAC entry is excluded from TUN capture. Private and link-local ranges are excluded from TUN routing by default, and additional bypass CIDRs can be added. The client list is read from Linux interface, route, and neighbor data using fixed read-only ip -j queries. The Backend may open AF_NETLINK for these reads but has no network-administration capability.

TUN-only mode also starts Mihomo DNS on loopback and configures port-53 hijacking for the router's own requests. This keeps the router's local resolver working without enabling LAN auto-redirect. The separate DNS takeover option enables LAN DNS forwarding through Mihomo. Neither mode edits `/etc/resolv.conf`, DHCP, or RoceOS DNS settings. Recommended mode uses the configured DoH endpoints; custom mode accepts up to four unicast IP addresses, including LAN DNS servers.

Changing active capture settings requires turning capture off first. Enabling any capture feature tests the generated config, snapshots the previous app config/state, and arms a four-minute rollback timer. Confirm only after SSH, the management page, DNS, IPv4/IPv6, and Internet access work. Use the Network page's recovery action to stop all capture features. Mihomo cleans up the TUN interface, routes, and its own redirect rules when its service stops. The helper never flushes nftables or removes routes owned by sing-box, Docker, iNextOS, or IPTV.

The protected TUN-only test on formal version `1.0.0` confirmed IPv4 and IPv6 default traffic routes through `mihomo0`; IPv6 policy rules at priority 8700 precede iNextOS's existing priority-8800 main-table rule while its priority-8500 rule remains earlier. With TUN active and Mihomo in Direct mode, IPv4 and IPv6 HTTPS requests returned HTTP 200 and the management health endpoint remained reachable. In Rule mode, IPv6 traffic entered TUN, but the selected proxy did not complete an IPv6 HTTPS request; that proxy node's IPv6 egress is not validated by the successful Direct-mode test. The four-minute rollback timer stayed active, SSH remained available, and the capture was then disabled. Afterwards IPv4 and IPv6 routes returned to `ppp0`, the rollback timer was inactive, Mihomo was stopped, and public IPv6 HTTPS on `:8844` still returned HTTP 200. LAN proxy, selected-device bypass, DNS takeover traffic, and router reboot behavior remain unverified.
